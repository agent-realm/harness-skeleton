## What is built

`hs`, a reference adapter speaking the `hs/0.2` protocol (§7), in this repository. It builds
what is left of questions 4 and 6 (§14, question 4) without settling them. It is one
conforming implementation among any others (§7.3, question 12); whether it stays the
reference after v0 is still open.

- **Node.js 22 or later, plain ES modules, one dependency.** `smol-toml` (BSD-3-Clause, no
  dependencies of its own, pinned exactly in `package-lock.json`, installed with
  `--ignore-scripts`) reads TOML, which spec layers and Codex's config use. It was added in
  milestone 2: reusing a TOML 1.0 parser beats writing one (AGENTS.md rule 3).
  - **Error messages:** the library's messages quote the source, so `src/files.js` reports a
    parse failure by line and column only.
  - **Unsafe keys:** `__proto__` and `constructor` keys are refused
    (`unsafeKeyBehaviour: 'throw'`).
  - **Why 1.9.1:**
    - 1.9.0 (2026-09-22) is the first version with that option and with the fix for
      GHSA-r4xh-jqrq-34v2, a parser denial of service;
    - 1.9.1 (2026-10-09) only adds "reject invalid extra exponent sign", a stricter parse.
  - **Future bumps:** wait 14 days after publication unless they fix a security advisory, and
    are checked against the registry's integrity hash.
  memhouse's session readers are JavaScript, so an `hs` driver can reuse one
  through a shim (§7.3). The `harness_path` rule names Node's `fs.realpathSync.native` as a
  resolver that gives the on-disk case (sessions-model §1). With no build step, the unit tests
  stay light enough for any workstation.
- **Layout:** `bin/hs.js` (the CLI), `src/` (the core: protocol, host, `harness_path`, the
  inventory, defaults), `src/drivers/<harness>/` (a driver per harness:
  `descriptor.js` holds the harness descriptor as data with a source on every fact, the
  other files hold the logic), `test/` (unit tests on fixture folders).

## Rules for the build

- One PR per milestone, from a new branch off `main` in its own worktree, reviewed before it
  merges, with green CI.
- **Unit tests never start a real harness and never read a real data folder.** They build
  fixture folders in a temp directory, and stand in a stub script for a harness binary.
  Conformance runs (tiers 1 to 3) run on disposable benches only: a VM made for it, or a CI
  runner, never a workstation (`conformance/README.md`).
- **When `hs` runs a harness binary itself** (`detect`), it runs it with HOME, the four XDG
  roots, TMPDIR and the binding variable all pointing into a fresh scratch directory. It
  checks those variables before the spawn, passes nothing else through except PATH, and
  removes the directory afterwards.
- **Secrets are references only** (§5.3). `credentials` paths are stat-ed, never read
  (§9.2), and a test proves it.
- **The retention default is one constant.** `DEFAULT_RETENTION_DAYS` in `src/defaults.js`
  is 9999 (question 8), and a test fails if the value appears anywhere else in `src/` or
  `bin/`. `describe` reports it under `defaults`, with its status.

## The spec package (the reference harness's R2s)

As decided in the reference-harness note (question 5): `src/spec/` moves into
`packages/skeleton-spec` (`@agent-realm/skeleton-spec`), which hs and the reference harness both
import, so the harness never imports hs's internals. It holds `layers.js`, `validate.js`, the
process checks `validate` uses (`process-checks.js`, from `src/process.js`) and the file readers
(`files.js`). hs's `src/spec/layers.js`, `src/spec/validate.js` and `src/files.js` re-export it,
and `src/process.js` re-exports `processProblems`, so hs's imports and its tests are unchanged.
The package's own test checks its exports, and that it imports only `node:` builtins, its own
files and `smol-toml`, never hs.

## Open items

- **A Codex launcher on the app-server.** `codex app-server` takes the RPC `skills/extraRoots/set`,
  which adds a skill root for a thread without writing anything (Codex 0.160.0, source). A launcher
  that drives the app-server could carry skills at launch, which `codex exec` and the TUI cannot.
  Not now.
- **Codex skills under a temp `HOME`, working directory or `CODEX_HOME`**: each reaches a skill root
  at launch, at the cost of the agent's home, workspace or state. They change what the user works
  in, so none is built.
