## 0. Summary

Every layer of the sessions stack has a standard and a reference implementation except the
producer. sessions-model is the record format, the session-adapters package reads twelve
harnesses into it, sessions-sql stores it, memhouse captures through it, and hs launches and
configures harnesses. What produces sessions is always someone else's harness, read from the
outside, with gaps the adapters can only name: an id that is not native, an operation the store
does not record, a usage basis no vendor documents.

The reference harness closes that gap. It is a small agent loop whose own session store is
sessions-model records, written through a library (the writer, §3). It exercises every record
type, part kind, link kind and lifecycle operation the contract defines (§2), and it reads the
skeleton spec natively (§6). Its adapter is nearly trivial, and every conformance check, in the
package and in hs, gains a harness that produces each feature on purpose, with a scripted model
(§5) and byte-stable fixtures.

It is a conformance reference, not a product. It competes with no harness, and §12 says what it
will never be.

## 1. Why, and what it is not

- **The gap.** Today each feature of sessions-model is proven, if at all, by whatever harness
  happens to produce it. Some features have no producer:
  - the `clear` link and the `clear` lifecycle operation are "none observed" (M §2.5, §2.6);
  - `continuation` is reserved and unobserved;
  - no adapter can show both a retraction-style and a destructive rewind on one harness.

  A conformance check without a producer is unverified, and the contract already marks one
  (Anchored ids: no fixture yet).
- **The reference.** One harness that produces every feature deterministically:
  - each `explicit` facet of its adapter has a fixture made by running the harness, not written
    by hand;
  - each fixture is regenerated by re-running its scenario, so the fixtures, the harness and the
    contract cannot drift apart unnoticed.
- **What it cannot prove.** The writer, its adapter and the fixtures all come from one reading
  of the contract, so a misreading would be consistent across all three and pass every check.
  The reference proves two things: that the pipeline round-trips, and that every feature has a
  producer. It does not prove that the reading matches how real harnesses behave. Real-harness
  fixtures, the lab captures and the live checks stay the evidence for that.
- **Not a product.** It has a line-based terminal interface good enough for a pty driver, a
  headless mode, and the tools the features need. It has no editor integration, no sandbox, no
  plugin marketplace, and no ambition on output quality (§12).

## 2. Scope: the smallest loop that exercises everything

The rule for scope: a feature is in when sessions-model or the hs standard defines it. A feature
is out when it is a product concern. Each row names how the loop produces the feature and which

- **A sub-agent's finish** needs no record: it is the spawning call's `tool_result`, by its

## 3. The writer library

A package, `@agent-realm/sessions-writer`. It writes sessions-model records into a store, so a
harness never builds a record by hand.

### 3.1 The store

- **Layout:**
  - one session is one append-only UTF-8 JSONL file, `sessions/<session_id>.jsonl`, under the
    harness store;
  - a child session (fork, subagent, rewind copy, clear, continuation) is its own file, with the
    link stated on the child. A scenario option also states it on the origin, so the consumer's
    merge of two statements into one edge (`stated_on: both`, M §2.5) has a producer: a `subagent`
    stated by the child's link and the origin's `spawn_agent` call, and a `fork` stated on both
    sides.
- **Units:** each line is one record in its final normalized form, the sessions-model shape with
  `session_id` and `incarnation` in every line, without `host`, `harness` and `harness_path`,
  which the adapter adds from the binding. A revision appends the record again under the same
  key, and the last line wins. The writer never rewrites a line.
- **Completeness:** by default a record is written only when complete. A writer mode, set by a
  scenario option, instead appends an in-progress message with `status: streaming` and then its
  final revision. Derive then holds that message's key, and its usage, until the revision
  arrives, so the Held check (S §2) has a producer. The growth check's cuts in mid-line still
  cover a partial last line, which `read` holds back as `readStream` does.
- **A malformed line:** a complete line that does not parse or fails validation makes `derive`
  raise `damaged` (retryable, reported), never skip it.
- **Ids:** all native and stable: session, message, part, call, usage, lifecycle. They come from
  a clock and a counter the writer owns, both injectable so a test run is byte-stable. `order` is
  a zero-padded counter.
- **Generations:** a destructive operation writes the session's new state to a new file and
  renames it into place. That is a new inode, so the adapter's stream reader sees a `reset`
  (S §2), and the consumer tombstones the keys that vanished. Two operations use it, both behind
  flags and off by default: `/rewind --destructive`, and `/delete <message>`, a message-level
  delete with its `delete` lifecycle record (M §2.6, shape b). This is the one place a file is
  rewritten, and it exists to exercise reset and tombstones on purpose.
- **The incarnation:** the writer mints a random `incarnation` at `create`, and it is the birth
  marker under `reuse: detected` (M §1, rule 2). A deleted session and a new one under the same id
  therefore differ. The adapter reads it from the first line, in `list` and in `derive`. A line
  whose `session_id` or `incarnation` disagrees with its file is `damaged`.
- **Secrets:** the writer redacts the value of every tool argument its schema marks `x-secret`,
  with the M §4 marker, so a real secret never reaches the disk. A test-only option keeps a
  sentinel value there instead. That is how the adapter's read-side redaction, the name lint and
  the conformance sentinel check keep a producer. Synthetic fixtures carry only the sentinel.

### 3.2 The API

A sketch, to be refined in the writer's own PR:

```js
import { openStore } from '@agent-realm/sessions-writer';

const store = openStore({ harnessPath, harness, clock, ids });   // clock and ids injectable
const s = store.create({ cwd, title, mode, kind });              // writes the session record
const m = s.message({ role: 'assistant', source: 'model', agentId: '', requestedModel, servedModel, responseId });
m.part.text('…');
m.part.reasoning({ text: '…' });                                 // or { opaque: true, signatureLen }
const call = m.part.toolCall({ name: 'shell', args: { command: 'ls' } });
m.finish('complete');                                            // the message reaches the file only here
s.usage({ anchor: { response: responseId }, input, output, cacheRead, cacheWrite, reasoning, inputIncludesCache, outputIncludesReasoning, granularity: 'per_response', model });
const r = s.message({ role: 'tool', source: null });                // null: nobody in the enum sent it (M §2.2)
r.part.toolResult({ callId: call.id, output, exitCode: 0, isError: false, status: 'completed' });
r.finish('complete');
s.lifecycle({ op: 'rename', target: { session: true } });        // and every other op
const child = s.link('fork', { at: messageId, inherits: { throughMessageId, idsPreserved: true } });
s.retract({ from: id, through: id });                            // rewind by retraction
s.close();
```

- **Validation:** each call checks its record against the contract before writing, with the
  package's validator (`@agent-realm/harness-session-adapters/validate`, to be exported at R3 from the
  invariant pass the package runs over every golden). So the writer and the
  conformance checks can never disagree on what a valid record is. An unknown field, a missing
  key, a link without its point, or `source: 'model'` on `role: 'tool'` is a thrown error, never a
  dropped field.
- **Hashing:** the writer computes no hash. `content_sha` and `cmp_sha` are the reader's, made
  by the package's one implementation (`src/records.js`, `seal`), so writer and reader can never
  hash differently.

### 3.3 The adapter is nearly the identity

The adapter lives where every adapter lives: `src/harnesses/<id>/` in the session-adapters
package, maintained with memhouse.

- `read` is the package's `readStream`: byte-offset JSONL, one unit per complete line.
- `derive` parses each line, keeps the last version of each key, adds the binding's part of the
  session key, seals each record, and computes two session fields: `fingerprint`, from the current
  line's messages, and `updated_at`, the latest `ts` the writer wrote. Every other session field
  is the writer's: it appends a session-record revision at each change (`/rename`, `/archive`,
  `/pin`, a `cd` that changes `last_cwd`).
- `describe` states every lifecycle and linkage facet as `explicit`.

That is close to the identity, but not the identity, and the note says so plainly. `derive` must
still produce `live`, `held`, `state` and `checkpoint`. The session fingerprint covers every
message on the current line, so derive computes it: storing it would mean re-appending the
session record after every message. And sealing belongs to the reader, as said above. What is
the identity is the content: every field of every record is what the writer wrote, except the
seals, `fingerprint` and `updated_at`, which the reader computes. A property-style test checks
exactly that (§9.2).

## 4. The loop

- **Front ends:**
  - `refh exec "<prompt>"`, headless;
  - `refh`, interactive. Its line-based terminal interface keeps the screen plain enough for a
    pty driver to read.

  The harness id is `reference-harness`, and the binary is `refh` (§11.2, question 1).
- **A turn:** the user message; the model's response, streamed to the screen and written when
  final; any tool calls, run and answered with tool results; the next model request, until the
  model ends the turn.
- **Tools:**
  - `shell`: a command, its exit code apart from the output, a timeout and cancellation;
  - `read_file` and `write_file`, with an image read as an attachment;
  - `spawn_agent` (inline or session mode);
  - the tools of each MCP server, named `mcp__<server>__<tool>`;
  - `skill`, which loads a skill's body.
- **Commands:** `/fork`, `/rewind <n> [--copy|--destructive]`, `/edit <n>`, `/clear`,
  `/compact`, `/continue`, `/rename`, `/archive`, `/unarchive`, `/pin`, `/unpin`,
  `/delete <message>` (behind a flag), `/delete-session`, `/resume <id>`, `/cancel`, `/quit`.
  Each one writes its record.
- **Compaction:** at a token threshold or on `/compact`. The model is asked for a summary, which
  is written as a `summary` part replacing the messages before `first_kept_id`; those stay
  current. The summary's usage is anchored to the compaction.

## 5. The model client

- **Wires:** three, behind one interface. Each streams over SSE and maps the vendor's events to
  the writer's parts:
  - Anthropic Messages;
  - OpenAI Chat Completions;
  - OpenAI Responses.
- **Usage flags by wire,** following the contract's table (M §2.4):
  - Anthropic Messages: `input_includes_cache: false`, `output_includes_reasoning: true`;
  - OpenAI Chat Completions and Responses: `true` and `true`.

  The numbers are copied as returned, never converted (M §2.4). Two wires that differ in their
  flags is the point: the Usage check sees both combinations from one harness. A gateway that
  translates between vendors may not keep a wire's definition. The flags then say what the wire
  defines, and a discriminating observation can overturn them, by the contract's rule. Its table also
  has true/false (Gemini) and false/false (OpenCode v1). A test-only option of the scripted model
  that declares a wire's flags lets the Usage check see all four combinations; a Gemini wire is a
  possible later addition.
- **Endpoints:** the spec's `[endpoints.<wire>]`, with the credential as a reference, resolved
  by the caller into the launch environment (hs's rule, §5.2 of the design note). A gateway that
  serves several wires, such as 9router, works unchanged. Nothing is ever written to the store
  but the endpoint's wire and the served model.
- **The scripted model,** for deterministic tests. A small server that speaks all three wires
  from a script:
  - each step matches a request (by turn, by a tool result it carries, or by a marker in the
    prompt);
  - each answer is a response: text, reasoning (plain or opaque), tool calls, usage numbers, an
    error, or a stall that ends in a timeout.

  It is its own package, `@agent-realm/scripted-model` (since R2;
  [its README](../../packages/scripted-model/README.md) is its spec). hs's tier 1 checks script
  Codex through it (`conformance/lib/bench.mjs`, `model()`), and the reference harness's tests and
  gentar scenarios use it too; a scenario starts its command in a setup step (§9.4). It binds
  `127.0.0.1` only. With no token, loopback is what keeps another process on a shared bench from
  driving a run, as for hs's bench listeners. It records requests by names only, never a prompt,
  a tool's output or a credential's value.

## 6. The skeleton spec, natively

- **Configuration:** the reference harness's own configuration format is the skeleton spec:
  `spec.toml` layers and `local.toml`, with the layer order and merge rules of design note §5.1.
  So its hs driver is close to the identity too:
  - its descriptor maps every skeleton item to itself;
  - overlay passes layers at launch;
  - materialize writes layers into its folder.

  hs's conformance checks then run against two kinds of harness: one mapped (Claude Code, Codex)
  and one native.
- **Its folder:** the binding of design note §8, with the path classes of §9 declared in its
  descriptor:
  - `config` for its layers;
  - `sessions` for `sessions/`;
  - `history` for prompt history;
  - `skeleton` for hs's records.
- **One spec resolver.** The spec resolver and validator that hs uses (`src/spec/`) become a
  workspace package that both import (§11.2, question 5), so the harness and the adapter can never
  read one spec two ways.

## 7. Its surface, and the setup on each session

- **The surface.** From harness2: the reference harness publishes its editable surface as data,
  in the manner of harness2's `SurfaceSpec`. That is eight components, each mapped to where it
  lives:
  - the system prompt;
  - guardrails;
  - memory (`AGENTS.md` and its imports);
  - tool guidance (descriptions);
  - sub-agents (`agents/<name>.md`);
  - skills (`skills/<name>/SKILL.md`);
  - scripts (files a skill or prompt names);
  - plugins and hooks (`[hook.*]`).
- **No silent failure.** harness2 checks each framework's silent drop rules from the outside:
  a skill without a description is dropped at load, a malformed hook never fires. The reference
  harness has none to check. Its loader refuses, at start, every component it cannot use, with
  the reason. `refh check` runs the same loader without starting a session, and reports each
  component as loaded or refused. That is AGENTS.md rule 5 (no silent degrade), applied to a
  harness's own loading.
- **What was live, and what was used.** Beyond harness2's static checks, each session records
  which components were live (with the digest of each) and how often each one fired: skill
  loads, sub-agent spawns, hook calls, script calls, MCP tool calls. harness2 records this on one
  path only (its LAB runner's `metrics.json`).
- **The setup fingerprint** (M §8, item 1). The contracts' owner's answer (§11.2, question 4): `setup`, an
  optional object on the session record, `null` unless the harness store records it. Adapters read
  it and never compute it from outside. The reference harness is its own launcher, so the join
  problem of §8 does not arise: it writes `setup` at the session's creation. The fields:
  - `launch_digest`: hs's, or null when started outside hs;
  - `surface`: each component's sha256;
  - `system_prompt_sha256`;
  - `tools`: their names;
  - `digest`: the sha256 of the canonical JSON of the rest.

  `harness_version` is already a session field, and the served model is per message and usage, so
  neither is repeated. That is more than harness2's run mark, which hashes the harness tree alone.
  It holds hashes and names only: never the rendered text, never an environment value, even one
  that looks harmless.

  `setup` is the setup at creation. A resume under a different setup writes its new `digest` in
  its `session.resume` notice. R1 lands before any milestone that writes records, so the harness
  needs no interim form.

## 8. Language and home

- **Home:** three packages in the harness-skeleton repo, beside `packages/harness-session-adapters`:
  - `packages/sessions-writer`, the writer (§3);
  - `packages/scripted-model` (§5);
  - `packages/reference-harness`, the loop (§4), with the `refh` binary.

  The adapter goes into `packages/harness-session-adapters` (§3.3).
- **Language:** JavaScript on Node.js 22+, ESM, like hs and the package.
  - The hashing, the stream reader, the spec resolver and the conformance runner are already
    there. One language means one implementation of each.
  - One CI, one test runner (`node:test`) and one dependency policy: node builtins only for the
    writer and the scripted model, as the package has. The loop takes `smol-toml`, already
    pinned, for the spec.
  - gentar is Python, but it drives the harness at a pty and reads its store through a command,
    so the harness's language does not matter to it.

## 9. Tests

### 9.1 Units

`node:test`, with the scripted model in-process and no network: the writer's validation and
generations, each wire's event mapping, each tool, each command's record.

The harness is real (its shell tool runs commands), and AGENTS.md's testing rule says unit tests
never start a real harness. So the unit tests keep these rules, stated in the package's README:
- The shell tool runs through an injectable executor, which the tests replace with a recorder.
- A test that runs the real executor runs only scripted, harmless commands, in a temp directory,
  with an empty environment but `PATH`.
- No test reaches the network: the scripted model runs in-process, or on `127.0.0.1`.

### 9.2 The writer and its adapter

- **Round trip:** for any sequence of writer calls, derive over the units the adapter reads
  gives exactly the records the writer wrote, field for field, plus the reader's seals and the
  fingerprint. The test generates sequences from a seed, so a failure reproduces.
- **The package's conformance:**
  - golden equality, the growth check, stable keys, the name lint, the rewrite reset, `list`,
    and the errors;
  - every `explicit` facet backed by a fixture that produces it.

  Each fixture is a store made by running a scenario against the scripted model. Its golden is
  reviewed by hand at every regeneration, as every golden is (`conformance/golden.js`).
- **Public fixtures:** they go into a public repository and through `test/public-fixtures.test.js`.
  So scenario runs use a fixed synthetic cwd and home (`/home/user/work/toyshop`, as the other
  fixtures do), the injected clock and ids, and shell commands whose output carries no bench host
  name or path.

### 9.3 Tier 2

S says "a scripted conversation read back exactly" belongs to harness-skeleton, against a
scripted endpoint. The reference harness is the first harness where that check can be exact,
since every id is native and the script fixes every value.

### 9.4 gentar

The harness comes in as a gentar subject, through the own-arena kit (`subject-template/`), with
scenarios in `gentar/scenarios/*.toml`. This is gentar's answer of 2026-10-23 (§13): it does not
offer its pty driver as a library.

- **Driving:** driver turns (`answer`, `expect`, `pick`, `key`).
  - An `expect` turn is one of two kinds. A `pattern` turn is a case-insensitive regex searched
    in the rendered screen. A `judge` turn is the semantic judge, which needs `data = "synthetic"`
    on the scenario and the judge key. This harness's checks are `pattern` turns: deterministic,
    and needing no key.
  - While it waits on any `expect`, the driver presses Enter on a screen that looks like an
    ordinary approval prompt, and aborts on danger-gate text. So the harness asks nothing that
    looks like an approval unless a scenario means it to.
- **The store:** checked by oracle assertions, never by the agent's word. `[[verify.commands]]`
  runs the adapter's `read` and `derive`, or a query over the records. `[[verify.files]]` checks
  the store's files.
- **The model:** the scripted model starts in `[oracle] steps`, which run before the driver turns,
  each step its own exec in the sandbox.
  - The step starts the model detached and waits for its port in the same step. That a process
    started this way outlives its exec on sbx is to be tested once on a bench before relying on
    it.
  - The model's URL (`127.0.0.1` in the same sandbox) goes in `[driver] command`, not `pass_env`,
    which carries values from the runner's environment.
  - Anything secret is routed in the kit's `gentar/policy.toml` (`[secrets] route`), and the
    scenario still declares each name.
- **Where things live:** steps and verify commands run in the bench, in the subject's pushed
  checkout. The adapter, the reader commands and the scripted model are in this repository, so
  they are there; anything else is installed in a step.
- **The engine:** pinned (`GENTAR_REF`), at v0.10.0 today, written for 0.11.0.
  - Under 0.11.0 the driven program must have exited 0 when the last turn is done, or the last
    turn presses `ctrl-c`, so each scenario ends with `/quit`.
  - Only these keys are allowed (unknown keys are refused under 0.11.0, and silently ignored
    under v0.10.0, so the scenarios use only these): `[[verify.commands]]` takes `command` and
    `contains`; `[[verify.files]]` takes `path` and `contains`; `expect` takes `pattern`, `judge`
    or `timeout`.
- **hs's status-line checks** use the same route: one `pattern` turn after a launch with the
  status line, and a second scenario after `plan` and `apply`.

### 9.5 memhouse

- **End to end:** a scenario runs on a bench, memhouse captures the store into a disposable
  ClickHouse, and a query compares what it holds with what the writer wrote.
- **Discovery:** `refh` states a default store folder (its data folder when started without
  one), so memhouse can discover it the way it discovers every other harness's store.
- **What it compares:** memhouse's session tables, once they follow the sessions-sql profile,
  which memhouse plans. Until then, the check states which projection it compares against.
- **The named checks:**
  - removed versions are never counted as live;
  - held keys are absent until their record completes;
  - both usage flag sets arrive as written;
  - a new incarnation is a new session;
  - a link stated on both sides is one edge.
- **The dependency:** this needs memhouse capturing through the package. By a decision
  of 2026-10-23 (§13), memhouse's release is paused, and memhouse switches to the package before
  it, as the first user of a concluded sessions-model. So no memhouse reader is written for this
  harness: once memhouse captures through the package, registering the adapter there is all it
  takes.

### 9.6 hs

hs's tier 1 checks (launch receipts, overlay precedence, MCP, hooks and skills at launch, and the
persisted items) gain a native harness to run against, beside Claude Code and Codex.

## 10. Safety

- **Where it runs:** the shell tool runs what the model asks. So the reference harness runs where
  conformance runs: on benches (disposable VMs, gentar's benches, CI runners), with the scripted
  model. A real model is for a bench only, never the user's workstation or a real data folder.
  This is AGENTS.md's rule for conformance runs, and the harness's own README states it.
- **No sandbox** in v0 (§12). This is said plainly, so nobody takes the harness for one.
- **Secrets:**
  - by reference only, resolved by the caller at launch;
  - never written to the store, its records or its logs: the writer redacts `x-secret` arguments
    itself, and only a test-only option keeps a sentinel (§3.1);
  - the shell tool's environment scrubbed by default;
  - transcripts treated as sensitive, since free text is out of reach of redaction (M §4).

### 11.2 Answered

All eight questions are answered. Questions 1 to 4, the contracts' owner's, become milestone R1, a
contract PR.

1. **The harness id:** `reference-harness`. The closed list names programs, not binaries, so the
   binary stays `refh`. Answered by the contracts' owner, and confirmed as the harness's name on
   2026-10-23 (§13).
2. **Resume, end, and a sub-agent's finish:** no new lifecycle operations in v1. Resume and end
   are `notice` parts (`session.resume`, `session.end`), and a sub-agent's finish is the spawning
   call's `tool_result`. This is to be revisited when a real harness store records them.
   Answered by the contracts' owner.
3. **`continuation`:** yes, with the reference harness as its first producer. The meaning is
   sharpened against its neighbours: a summary, not messages (unlike `fork`), and something
   rather than nothing (unlike `clear`). `at` stays a message id, the origin's compaction point,
   not a lifecycle id. The conformance item is marked "proved by the reference harness only".
   Answered by the contracts' owner.
4. **The setup field:** `setup`, an optional object on the session record, with the contents
   in §7. Joining hs launch records onto other harnesses' sessions is consumer-side and out of v1.
   Answered by the contracts' owner.

5. **The spec package:** extract `src/spec/` into `packages/skeleton-spec`, which hs and the
   reference harness both import. The harness never imports hs's internals. It is its own PR,
   with hs's tests unchanged (R2s). Answered 2026-10-23 (§13); built.
6. **Ownership:** the adapter belongs to the session adapters package. The writer and the
   scripted model are this repository's, reviewed by the package's maintainer. The package gains
   a validator export at R3, which the writer imports. Agreed 2026-10-23.
7. **memhouse before its release:** answered by a decision of 2026-10-23 (§13). memhouse switches to
   the package before its release, so no extra memhouse reader is written, and R9 depends on
   that switch, not on the release.
8. **Destructive rewind:** kept, behind a flag, off by default, as the one way to exercise reset
   and tombstones on purpose. The message-level delete reuses its generation mechanism. Answered
   2026-10-23.

## 12. Out of scope

- A product: polish, an editor or IDE integration, themes, a plugin marketplace, settings
  screens.
- A sandbox, or any claim of isolation. It runs on benches.
- Output quality, prompting craft, planning, and anything a real harness competes on.
- Windows, several writers to one store, and very large sessions.
- MCP OAuth, and connectors behind a login.
- Cost accounting beyond copying the numbers the endpoint returns.
- A store format of its own beyond sessions-model records: if the contract cannot say it, the
  harness does not store it, and §11 asks instead.
