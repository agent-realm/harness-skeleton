## 2. Scopes and precedence

Documented order, highest first [D-basic]:

1. CLI flags and `-c/--config key=value` overrides (also `--enable/--disable <feature>`)
2. Project `.codex/config.toml` files, ordered root-to-cwd, closest wins, **trusted projects only**
3. Profile file selected with `--profile <name>` (`$CODEX_HOME/<name>.config.toml`)
4. User `$CODEX_HOME/config.toml`
5. Cloud-managed config defaults
6. System `/etc/codex/config.toml` (Unix)
7. Built-in defaults

Managed (enterprise) [D-managed]:

- **Defaults** (user can override): `/etc/codex/managed_config.toml` (Unix), `~/.codex/managed_config.toml` (Windows), MDM key `config_toml_base64`. Order as summarized by the fetcher: MDM > `managed_config.toml` > user `config.toml` > CLI.
- **Requirements** (constraints, cannot be overridden): `/etc/codex/requirements.toml`, cloud-delivered "Agent Security" requirements, MDM key `requirements_toml_base64`. Constrains `allowed_approval_policies`, `allowed_sandbox_modes`, `allowed_permission_profiles`, `mcp_servers` allowlist (name + identity), `[rules]` (prompt/forbidden prefix rules), `[features]` pins, `[experimental_network]` domain rules, `allow_managed_hooks_only` (only valid in `requirements.toml`) [D-managed], [G-docs].
- Source layer names in code: `PackagedDefaults`, `Mdm`, `EnterpriseManaged`, `System`, `User`, `Project`, `SessionFlags`, `LegacyManagedConfigTomlFromFile`, `LegacyManagedConfigTomlFromMdm` [S-ext/skills/src/host_roots.rs].

**The loader's order, read in source 2026-10-22** [S-config/src/loader/README.md][S-config/src/config_layer_source.rs], at `rust-v0.160.0`. Top overrides bottom, with each layer's `precedence()`:

1. `LegacyManagedConfigTomlFromMdm`: MDM-delivered `managed_config.toml`, "while it is being phased out" (50).
2. `LegacyManagedConfigTomlFromFile`: `managed_config.toml` (40).
3. `SessionFlags`: CLI overrides, applied as dotted-path TOML writes (30).
4. `Project`: `.codex/config.toml`.
5. `User` profile config, when present.
6. `User` config, `config.toml`.
7. `EnterpriseManaged`: cloud-managed config bundle layers (15).
8. `System`: `/etc/codex/config.toml` (10).
9. `Mdm`: managed preferences delivered by MDM (0).

"The managed layers remain above project and session layers in the final stack." The legacy `managed_config.toml` therefore outranks the user config and every launch layer: it is policy, not a default. That settles the two readings above, and it agrees with the fetcher's summary, not with the docs' "user can override". The non-legacy MDM preferences rank lowest. Requirements (`requirements.toml`) are a separate mechanism, not a layer in this stack.

Project discovery and trust:

- Codex searches from cwd upward to the project root, marked by `project_root_markers` (default `[".git"]`), loading every `.codex/config.toml` on the way; relative paths resolve against that `.codex/` folder [D-adv], [S-schema].
- Trust gate: `[projects."<absolute path>"] trust_level = "trusted" | "untrusted"` in the **user** config; the TUI trust prompt writes it [D-ref], [S-schema], [L-cfg]. Untrusted projects skip project config, hooks and rules [D-basic]; since 0.150.0 they also supply no project `AGENTS.md` [G-REL].
- Keys a project config cannot set: `openai_base_url`, `chatgpt_base_url`, `apps_mcp_product_sku`, `model_provider`, `model_providers`, `notify`, `profile`, `profiles`, `experimental_realtime_ws_base_url`, `otel` [D-adv].
- `/debug-config` shows "config layers and requirement sources" [S-tui/src/slash_command.rs]. `--strict-config` errors on unknown keys [L-help]. `codex exec --ignore-user-config` skips `$CODEX_HOME/config.toml` ("auth still uses CODEX_HOME") [L-help].

## 6. Endpoint / provider routing

- Select with `model_provider = "<id>"`; define with `[model_providers.<id>]` [D-ref], [D-adv]. Keys: `name`, `base_url`, `env_key` (name of the env var holding the API key), `env_key_instructions`, `wire_api`, `http_headers`, `env_http_headers` (header -> env var name), `query_params`, `request_max_retries`, `stream_max_retries`, `stream_idle_timeout_ms`, `requires_openai_auth`, `supports_websockets`, `websocket_connect_timeout_ms`, `supports_standalone_web_search`, `model_catalog_url`, `experimental_bearer_token` (discouraged), `[auth]` command token helper (`command`, `args`, `cwd`, `timeout_ms`, `refresh_interval_ms`), `aws.profile`/`aws.region` (Bedrock), `gateway_oauth` [D-ref], [S-schema].
- **`wire_api` accepts only `"responses"`** at 0.160.0 ("The Responses API exposed by OpenAI at `/v1/responses`") [S-schema] (verified). A third-party endpoint that only speaks Chat Completions cannot be used directly.
- Reserved provider ids (not overridable): `openai`, `ollama`, `lmstudio`; built-in `amazon-bedrock` [D-adv], [D-ref]. `openai_base_url` overrides the built-in `openai` provider's base URL [S-schema]. `OPENAI_BASE_URL` appears in the binary [L-bin]; not found in docs.
- Local OSS: `--oss` + `--local-provider lmstudio|ollama` or `oss_provider`; interactive CLI prompts if unset, `codex exec` errors [L-help], [D-adv]. `CODEX_OSS_BASE_URL`, `CODEX_OSS_PORT` appear in the binary [L-bin]; not documented.
- Routing keys are **not** settable from project config [D-adv]; they live in user config, a profile file, or `-c`.
- Pointing one launch at an OpenAI-compatible (Responses) endpoint: put `model_provider`, `model` and `[model_providers.<id>]` in `$CODEX_HOME/<name>.config.toml` and launch `codex -p <name>`, or pass `-c model_provider=<id> -c 'model_providers.<id>={name="...", base_url="...", env_key="...", wire_api="responses"}'` [D-adv], [L-help].

## 11. Hooks

- Present and on by default: feature `hooks` stable/true; disable with `[features] hooks = false` [D-hooks], [L-feat].
- Sources (additive, "Higher-precedence config layers don't replace lower-precedence hooks"): `$CODEX_HOME/hooks.json`, inline `[hooks]` in user `config.toml`, `<repo>/.codex/hooks.json`, inline `[hooks]` in `<repo>/.codex/config.toml`, plugin `hooks/hooks.json` [D-hooks]. Managed: `allow_managed_hooks_only = true` in `requirements.toml` [G-docs].
- **At launch, read in source 2026-10-22** at `rust-v0.160.0` [S-hooks/src/engine/discovery.rs, S-hooks/src/config_rules.rs, S-hooks/src/lib.rs, S-config/src/fingerprint.rs, S-config/src/hook_config.rs] (verified):
  - `-c hooks.<Event>=[…]` loads as the SessionFlags layer, key source `/<session-flags>/config.toml`, and needs trust.
  - `hooks.state` is read from the user and session-flag layers only, later winning per field, so `-c hooks.state={"<key>"={trusted_hash="…"}}` trusts a hook for one launch. A second `-c hooks.state` replaces the first.
  - Key: `<source>:<event label>:<group>:<handler>`, snake_case labels, indexes from 0.
  - Hash: `sha256:` and the hex of the canonical JSON (sorted keys, compact) of `{event_name, matcher (matcher events only), hooks: [normalized handler]}`, where the handler is `{type, command, timeout (default 600; SessionEnd 1..3), async}` and unset fields are left out.
  - Untrusted hooks are skipped silently under `codex exec`.
  - The SessionFlags layer is built from the `-c` overrides alone (`config/src/loader/mod.rs` `build_cli_overrides_layer`), and discovery reads each layer's own `[hooks]` and `hooks.json`, so a `-c hooks.<Event>` array replaces no other layer's hooks for that event.
  - **Measured** [B-hooks]: with hs's computed table the hooks ran, and without it they did not. The folder's own `PreToolUse` hook on `Bash`, trusted in `config.toml` by the same hash keyed by `<CODEX_HOME>/config.toml`, ran either way, beside a launch `PreToolUse` guard.
- **Execution and failure, read in source** (verified) [S-hooks/src/engine/command_runner.rs, S-hooks/src/events/pre_tool_use.rs, S-hooks/src/schema.rs]:
  - **Running:** `<zsh|bash|sh> -c <command>` with Codex's full environment; `shell_environment_policy` does not apply.
  - **PreToolUse lets the call through** on a spawn error, a timeout, an exit other than 0 and 2, a signal, exit 2 with an empty stderr, or JSON stdout that does not parse. A bare `allow` (without `updatedInput`) is a failed hook.
  - **Output:** output whose trimmed start is `{` or `[` is taken as JSON (`engine/output_parser.rs` `looks_like_json`), and one that does not parse is a failed hook; structs are `deny_unknown_fields`; `additionalContext` exists on PreToolUse, PostToolUse, SessionStart, UserPromptSubmit and SubagentStart.
  - **Matching and tool names:**
    - a matcher of only `[A-Za-z0-9_|]` is exact, anything else an unanchored regex;
    - the shell tool reports `Bash` with `{command}`;
    - `apply_patch` reports `{command: <patch>}`, with the aliases `Write` and `Edit`.
  - **Measured** [B-hooks]: a `PreToolUse` deny on `Bash` kept `exec_command` from running, and the reason reached the tool output. A `SessionStart` `additionalContext` reached the request.
- Trust: hash-based. New or changed hooks are skipped until reviewed in `/hooks`; state persisted as `[hooks.state."<file>:<event>:<group-idx>:<handler-idx>"] trusted_hash = "...", enabled = bool` in the user `config.toml` [D-hooks], [S-schema], [L-cfg]. Bypass: `--dangerously-bypass-hook-trust` [L-help].
- File shape is Claude Code's: `{"hooks": {"<Event>": [{"matcher": "...", "hooks": [{"type": "command", "command": "...", "timeout": 30}]}]}}` [L-hooks], [S-schema].
- Handler types: `command`, `mcp_tool` (`server`, `tool`, `input` with `${field.nested}` templating); `prompt` and `agent` parse but are skipped [D-hooks], [S-schema]. Command fields: `command`, `commandWindows`, `timeout` (s), `statusMessage`, `async`, `additionalContextLimit` (default 2,500 tokens; 0 disables spilling) [D-hooks], [S-schema].

## 17. Headless / non-interactive mode

## Surprises / things that do not map onto Claude Code's model

- **`CODEX_HOME` is not a full sandbox.** User skills at `~/.agents/skills` and the personal plugin marketplace under `$HOME` are resolved from the OS home, not `CODEX_HOME`. Two config roots on one machine share them. MCP OAuth tokens in the keyring are keyed by server name + URL, so they are shared too. CLI login does isolate: `auth.json` lives in the root, and the keyring account is a hash of the root path.
- **`CODEX_HOME` must exist.** If it points at a missing directory, startup fails; it is not created on demand. A launcher has to `mkdir` the directory first.
- **The default credential store is a plaintext file** (`auth.json`, mode 600). Keyring is opt-in through `cli_auth_credentials_store`. In Claude Code the macOS default is the Keychain.
- **Project config is trust-gated, and the trust list lives in the user config.** The list is `[projects."<abs path>"].trust_level`. An untrusted project contributes no config, no hooks, no rules and (since 0.150) no `AGENTS.md`. A harness-neutral standard has to model "trusted project" as a separate input.
- **Routing keys cannot come from a project.** `model_provider`, `model_providers`, `openai_base_url`, `notify` and `otel` are user/profile/CLI-only.
- **Only the Responses wire API is supported.** A Chat-Completions-only gateway cannot be plugged in through `model_providers`.
- **Profiles are whole files** (`$CODEX_HOME/<name>.config.toml`, overlaid on the user config). They are not named sections, and the old `[profiles.x]` form is rejected. This is the closest Codex analogue to a "playbook" overlay.
- **Hooks are near-wire-compatible with Claude Code.** They use the same `hooks.json` shape, mostly the same event names, the same stdin fields, `permission_mode` values copied from Claude Code, exit 2 for block, and `CLAUDE_PLUGIN_ROOT` aliases. Differences: there is no `Notification` event, there is an extra `Interrupt` event, and an `mcp_tool` handler type exists. Every hook also needs a **hash-trust approval** before it runs; trust is stored in `config.toml` and can be bypassed with `--dangerously-bypass-hook-trust`. A freshly installed hook is silently inert until it is trusted.
- **There is no custom status-line command.** `tui.status_line` only picks from a fixed menu of built-in items, so a Claude Code `statusLine` script has no equivalent.
- **There are no custom slash commands.** File-based prompts were removed in 0.118; the replacement is skills (`$name`). Claude Code plugin `commands/` are converted to skills at install.
- **Plugins accept the Claude Code layout.** Codex reads `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` alongside its own `.codex-plugin/` and `.agents/plugins/` paths and the Agent Plugins `plugin.json`. A single plugin repository can serve both harnesses.
- **Codex cannot be used as an MCP server** (`codex mcp-server` was removed in 0.154). The programmatic surface is the JSON-RPC `app-server` protocol.
- **Sessions live in a shared daemon, not in per-process registry files.** There is no `sessions/<pid>.json`. Discovery is `codex agents`, injection is `codex queue`, and `--no-daemon` opts out. Transcripts are still rollout JSONL files, but paginated SQLite thread history has been the default since 0.158. Any external transcript reader, such as memhouse ingest, should watch for the JSONL files becoming secondary.
- **Instructions are AGENTS.md only.** `CLAUDE.md` is ignored unless it is listed in `project_doc_fallback_filenames`. There is no `@import` syntax, and there is a 32 KiB total cap. `AGENTS.override.md` gives a per-directory override with no Claude Code counterpart.
- **Permissions are a different shape.** Claude Code uses tool-pattern allow/deny lists. Codex combines an OS sandbox (`sandbox_mode` and permission profiles with filesystem/network policy), an approval policy, Starlark prefix rules for shell commands, and per-tool approval modes for MCP and app tools.
- **`codex exec` is strict by default.** It runs in a read-only sandbox, refuses to start outside a git repo, and exits 1 for every failure class. Its exit codes are not documented.
- **The docs are thin and moving.** The GitHub `docs/` files are stubs, developers.openai.com redirects to learn.chatgpt.com, and the plugin file format is documented nowhere official. The generated `config.schema.json` at the release tag is the most reliable contract.
