## Local install note

- Installed with npm and `--ignore-scripts` (or with a postinstall that did not run), the `opencode` on PATH is `opencode-ai/bin/opencode.exe`, a stub that prints "opencode-ai's postinstall script was not run" and exits 1. The real binary is `<pkg>/node_modules/opencode-darwin-arm64/bin/opencode` (Mach-O arm64, 143 MB) and works directly. All local observations below use that binary. [L-help]

`<pkg>` = the global install's `opencode-ai` package directory.

## 1. Config root

OpenCode uses XDG base dirs via the `xdg-basedir` package, each with `opencode/` appended; on macOS this resolves to `~/.config`, `~/.local/share`, `~/.cache`, `~/.local/state` (not `~/Library`). [G:packages/core/src/global.ts] [L-paths]

| Root | Default | Relocated by | What lives there |
|---|---|---|---|
| config | `~/.config/opencode` | `XDG_CONFIG_HOME` | `opencode.json`/`opencode.jsonc` (+ legacy `config.json`, legacy TOML `config` auto-migrated), `tui.json`/`tui.jsonc`, `AGENTS.md`, `{agent,agents}/`, `{command,commands}/`, `{mode,modes}/`, `{plugin,plugins}/`, `{skill,skills}/`, `{tool,tools}/`, `themes/`; plus harness-written `.gitignore`, `package.json`, `node_modules/`, `package-lock.json`/`bun.lock` [D-config] [G:packages/opencode/src/config/config.ts] [L-bin] [L-home] |

Env vars that point at config (none is a full relocation):

| Var | Effect | Doc |
|---|---|---|
| `OPENCODE_CONFIG` | one extra config **file** layer | [D-config] |
| `OPENCODE_CONFIG_DIR` | one extra config **directory** layer (opencode.json(c), agents, commands, modes, plugins, skills, tools, tui.json); **also replaces** the global dir for `AGENTS.md` only (since v1.1.4/v1.1.51) | [D-config] [G:packages/core/src/global.ts] [R-v1.1.51] |
| `OPENCODE_CONFIG_CONTENT` | inline JSON layer | [D-config] |
| `OPENCODE_TUI_CONFIG` | extra TUI config file | [D-tui] |
| `OPENCODE_DB` | DB file (`:memory:`, absolute, or relative to data dir) | [G:packages/core/src/database/database.ts] (undocumented) |
| `OPENCODE_AUTH_CONTENT` | JSON used instead of reading `auth.json` | [G:packages/opencode/src/auth/index.ts] (undocumented) |
| `OPENCODE_MODELS_PATH` / `OPENCODE_MODELS_URL` | catalog source | [D-cli] (URL), [G:packages/core/src/flag/flag.ts] (PATH) |

**Does one variable relocate everything?** No.
- `OPENCODE_CONFIG_DIR` is **additive**: the XDG global `opencode.json` is still loaded and merged underneath it (verified: XDG `"share":"disabled"` survived while `OPENCODE_CONFIG_DIR`'s `username` overrode the XDG one) and skills from both dirs were listed together. [L-sbx] [G:packages/opencode/src/config/config.ts lines 398-430] Auth, sessions, DB, snapshots, logs, caches, state all stay in XDG data/cache/state. `opencode mcp add` and `opencode plugin -g` write to the XDG config dir regardless. [G:packages/opencode/src/cli/cmd/mcp.ts] `opencode debug paths` still prints the XDG config dir with `OPENCODE_CONFIG_DIR` set. [L-paths]
- Setting all four `XDG_*_HOME` to subdirs of one folder relocates config, data (auth, DB, sessions), cache and state (verified with `debug paths` and file creation in the sandbox). [L-sbx] What still escapes: `$TMPDIR/opencode`; `~/.claude/CLAUDE.md`, `~/.claude/skills`, `~/.agents/skills` (turn off with `OPENCODE_DISABLE_CLAUDE_CODE=1` + `OPENCODE_DISABLE_EXTERNAL_SKILLS=1`); `~/.opencode/` (scanned as a `.opencode` dir, verified with `OPENCODE_TEST_HOME`, no documented switch) [L-sbx]; project walk-up (`opencode.json`, `.opencode/`, `AGENTS.md`; `OPENCODE_DISABLE_PROJECT_CONFIG=1` turns these off); managed dir and MDM plist (always applied); remote/console org config tied to logins.
- Caveat for a standard: `XDG_*` set for the harness is inherited by every child (bash tool, MCP servers, LSPs, git, gh), relocating *their* config too. The `shell.env` plugin hook can undo it for shell calls; MCP servers take `environment` per server. [D-plugins] [D-mcp-servers]

## 2. Scopes and precedence

Documented order, lowest to highest (live site lists 9 entries incl. `OPENCODE_CONFIG_DIR` at 6; `dev` docs list 8 and describe `OPENCODE_CONFIG_DIR` separately as "loaded after the global config and `.opencode` directories"): remote `.well-known/opencode` -> global `~/.config/opencode/opencode.json` -> `OPENCODE_CONFIG` -> project `opencode.json` -> `.opencode` directories -> `OPENCODE_CONFIG_DIR` -> `OPENCODE_CONFIG_CONTENT` -> managed files -> macOS MDM (not user-overridable). [D-config]

Order actually implemented in 1.18.18 [G:packages/opencode/src/config/config.ts lines 316-560]:

1. Remote: for every `auth.json` entry of type `wellknown` (created by `opencode providers login <url>`), fetch `<url>/.well-known/opencode` (`config` + optional `remote_config.url`). [D-config] [G:config.ts]
2. Global: `<XDG config>/config.json`, then `opencode.json`, then `opencode.jsonc`.
3. `OPENCODE_CONFIG` file.
4. Project: `opencode.jsonc`/`opencode.json` found walking up from cwd to the git worktree root, farthest first (nearest wins). Skipped by `OPENCODE_DISABLE_PROJECT_CONFIG=1`.
5. Config directories, in this order: XDG config dir, project `.opencode/` dirs (walk-up), `~/.opencode/`, `OPENCODE_CONFIG_DIR`. Each `.opencode` dir and `OPENCODE_CONFIG_DIR` contributes `opencode.json(c)`; every dir contributes markdown agents/commands/modes and plugin files. [G:packages/opencode/src/config/paths.ts]
6. `OPENCODE_CONFIG_CONTENT`.
7. OpenCode console account org config (if logged in to an OpenCode console account; undocumented beyond Enterprise "central config"). [D-enterprise]
8. Managed dir `opencode.json(c)`.
9. MDM plist.
10. Post-processing: legacy `mode` entries become primary agents; `OPENCODE_PERMISSION` deep-merged into `permission`; legacy `tools` booleans converted to permission rules *below* explicit `permission`; `OPENCODE_DISABLE_AUTOCOMPACT`/`OPENCODE_DISABLE_PRUNE` applied.

Merge semantics: remeda `mergeDeep` -- objects deep-merge, scalars and arrays replace, **except** `instructions` (concatenated and de-duplicated across layers) and `plugin` (merged with origin/scope tracking, deduplicated by package name+version). [D-config] [G:config.ts lines 39-50] Unknown top-level keys are rejected with `ConfigInvalidError`; config is loaded once and not hot-reloaded. [L-skill]

TUI config has its own chain: global `tui.json(c)` -> `OPENCODE_TUI_CONFIG` -> project `tui.json(c)` walk-up -> `.opencode/tui.json(c)` and `OPENCODE_CONFIG_DIR/tui.json(c)`. [G:packages/opencode/src/config/tui.ts]

## 6. Endpoint / provider routing

- `provider.<id>` fields: `npm` (AI SDK package), `name`, `api`, `env` (env var names for the key), `id`, `whitelist`, `blacklist`, `options` {`apiKey`, `baseURL`, `enterpriseUrl`, `setCacheKey`, `timeout` (300000), `headerTimeout`, `chunkTimeout`, plus provider-specific ones such as Bedrock `region`/`profile`/`endpoint`}, `models` {`<id>`: `name`, `limit` {`context`,`output`}, `options`, `headers`, `variants`, `cost`, `modalities`, ...}. ## 7. Login / auth

- CLI: `opencode providers` (alias `auth`): `login [url] [-p provider] [-m method]`, `list`/`ls`, `logout [provider]`. TUI: `/connect`. [L-help] [D-cli]
- Storage: `<XDG data>/opencode/auth.json`, written with mode 0600; entry types `api`, `oauth`, `wellknown`. [D-providers] [G:packages/opencode/src/auth/index.ts]
- Other credential stores: MCP OAuth tokens in `<data>/mcp-auth.json` [D-mcp-servers] [L-bin]; OpenCode console account tokens in `opencode.db` (`account` table has `access_token`, `refresh_token`; there is also a `credential` table). [G:packages/core/src/database/schema.gen.ts]
- Env: provider keys named by models.dev (`ANTHROPIC_API_KEY`, ...), `AWS_PROFILE`/`AWS_REGION`/`AWS_BEARER_TOKEN_BEDROCK`, `GOOGLE_CLOUD_PROJECT`, `{env:VAR}` in config; `OPENCODE_AUTH_CONTENT` (undocumented) supplies the whole auth map as JSON. [D-providers] [D-config] [G:auth/index.ts]
- Isolation: auth lives in the **data** dir. Relocating `OPENCODE_CONFIG_DIR` does **not** isolate the login; `XDG_DATA_HOME` does (and `OPENCODE_DB` separates only the DB). [G:auth/index.ts] [L-sbx]

## 8. MCP servers

- `mcp.<name>`, discriminated by `type`. [D-mcp-servers] [S-schema]
  - local: `type: "local"`, `command` (string array, required), `cwd`, `environment`, `enabled`, `timeout` (default 5000 ms).
  - remote: `type: "remote"`, `url`, `headers`, `oauth` ({`clientId`, `clientSecret`, `scope`, `callbackPort` (19876), `redirectUri`} or `false`), `enabled`, `timeout`.
  - `{"enabled": false}` disables a server inherited from a parent layer. [L-skill] Global request timeout `experimental.mcp_timeout`. [S-schema]
- OAuth: automatic, Dynamic Client Registration (RFC 7591) when no `clientId`; tokens in `~/.local/share/opencode/mcp-auth.json`. [D-mcp-servers]
- Tool naming/gating: MCP tools are `<server>_<tool>`; disable globally or per agent with globs in `tools`/`permission` (e.g. `"mymcp_*": false`). [D-mcp-servers]
- CLI: `mcp add [name] [--url] [--env K=V] [--header K=V]` (interactive; offers project or global scope inside a git repo; edits JSONC preserving comments; global = XDG dir), `mcp list`/`ls`, `mcp auth [name]`, `mcp auth list`, `mcp logout [name]`, `mcp debug <name>`. [L-help] [G:packages/opencode/src/cli/cmd/mcp.ts]
- HTTP API: `GET /mcp` status, `POST /mcp` adds a server at runtime. [D-server]
- No `.mcp.json` (Claude Code project file) support: string absent from the binary. [L-bin]

## 9. Skills

- Supported, `SKILL.md` with YAML frontmatter, since v1.0.186 (2025-12-22); `.claude/skills` added v1.0.208; `.agents/skills` v1.1.50. [R-list]
- Discovery order in 1.18.18 (later wins on a duplicate `name`, with a logged warning) [G:packages/opencode/src/skill/index.ts]:
  1. `~/.claude/skills/**/SKILL.md`, `~/.agents/skills/**/SKILL.md`
  2. `.claude/skills/**`, `.agents/skills/**` in every directory walking up from cwd to the worktree root
  3. `{skill,skills}/**/SKILL.md` in every config dir: XDG config, project `.opencode/` (walk-up), `~/.opencode/`, `OPENCODE_CONFIG_DIR` (verified: XDG `skill/`, project `.opencode/skills/` and `OPENCODE_CONFIG_DIR/skills/` all listed together) [L-sbx]
  4. `skills.paths` (scanned for `**/SKILL.md`; `~/` and relative paths allowed)
  5. `skills.urls` (each serves an `index.json`; pulled into `~/.cache/opencode/skills`)
- Built-in skill `customize-opencode` (location `<built-in>`). [L-skill]
- Frontmatter: `name` (required, 1-64 chars, `^[a-z0-9]+(-[a-z0-9]+)*$`, must equal the folder name), `description` (required, 1-1024 chars), optional `license`, `compatibility`, `metadata` (string map). No `allowed-tools` equivalent documented. [D-skills]
- Loading: the model sees name+description and calls the `skill` tool to load the body; gated by `permission.skill` patterns (`deny` hides a skill); can be turned off per agent. [D-skills]
- Switches: `OPENCODE_DISABLE_EXTERNAL_SKILLS=1` (no `~/.claude`, `~/.agents`, project `.claude`/`.agents` scans), `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1`, `OPENCODE_DISABLE_CLAUDE_CODE=1`. [D-rules] [G:skill/index.ts] Listing: `opencode debug skill`. [L-help]
- Observed: user skill folders under `~/.config/opencode/skills/`. [L-home]

## 11. Hooks

No shell-command hooks: "hook" appears nowhere in [S-schema], and docs describe hooks only as plugin functions. [S-schema] [D-config] [D-plugins] The only config-declared commands that run on agent actions are `formatter` commands after writes/edits. [D-formatters]

Plugin hooks (from the `Hooks` interface) [G:packages/plugin/src/index.ts]. Semantics: every plugin's hook runs **in sequence** in load order and is awaited; hooks get `(input, output)` and **mutate `output` in place**; the return value is ignored [G:packages/opencode/src/plugin/index.ts `trigger`]. Throwing inside `tool.execute.before` aborts that tool call with the error message (docs `.env` example). [D-plugins]

## 12. Permissions

- `permission`: a string (applies to everything) or an object keyed by permission name; each value is an action (`allow`/`ask`/`deny`) or `{pattern: action}`. **Last matching rule wins** (put `"*"` first). `*` and `?` wildcards; `~`/`$HOME` expansion. [D-permissions]
- Keys: `read`, `edit` (covers write/patch/apply_patch), `glob`, `grep`, `list`, `bash` (matches parsed commands), `task` (subagent names), `external_directory` (paths outside the cwd), `lsp`, `skill` take patterns; `todowrite`, `question`, `webfetch`, `websearch`, `doom_loop` (same call 3 times) take only an action. Unknown keys accepted as pattern rules (e.g. MCP tool globs). [S-schema] [D-agents] [D-permissions]
- Defaults: **allow everything**, except `doom_loop` and `external_directory` = `ask`, and `read` denies `*.env`, `*.env.*` (allows `*.env.example`). [D-permissions] [D-config]
- Ask answers: `once`, `always` (patterns suggested by the tool, rest of the current session), `reject`. [D-permissions] Source also has a per-project saved-permission table in the DB (v2 core), not documented. [G:packages/core/src/permission/saved.ts]
- Per agent: `agent.<name>.permission` merged over the global one (agent wins); built-in `plan` agent = edits denied. [D-permissions] [L-skill]
- Auto mode: `--auto` (TUI and `run`; hidden aliases `--yolo`, `--dangerously-skip-permissions` on `run`) approves everything not explicitly denied; also a TUI palette toggle. [D-permissions] [G:packages/opencode/src/cli/cmd/run.ts]
- `OPENCODE_PERMISSION` (JSON) is merged into `permission` after all layers. Legacy `tools: {name: bool}` (deprecated v1.1.1) maps to allow/deny. [D-cli] [G:config.ts] [R-v1.1.1]
- No OS sandbox (no seatbelt/landlock equivalent) found in docs (searched permissions, tools, config, network). Policies (`experimental.policies`) gate resources such as providers, not tools. [D-policies]

## Surprises / things that do not map onto Claude Code's model

- **No single "home" variable.** Claude Code's `CLAUDE_CONFIG_DIR` relocates nearly everything; OpenCode's `OPENCODE_CONFIG_DIR` is an extra config *layer* on top of `~/.config/opencode`, and auth, sessions and caches stay in XDG data/cache/state. Real isolation needs all four `XDG_*_HOME` vars, which child processes inherit, plus switches for `~/.claude` and `~/.agents`. `~/.opencode/` is also read, with no documented switch.
- **Inconsistent use of `OPENCODE_CONFIG_DIR`**: it *replaces* the global dir for `AGENTS.md` but only *adds to* it for `opencode.json`, skills, agents and commands. Themes, `mcp add` and `plugin -g` ignore it.
- **The harness writes into config folders and repos**: it inserts `$schema` into config files, seeds a global `opencode.json`, writes `.gitignore`, runs `bun install` of `@opencode-ai/plugin` (`package.json`, `node_modules`) in every config dir including project `.opencode/`, migrates legacy TUI keys into `tui.json`, and writes `.git/opencode`. A playbook folder cannot be treated as a read-only template.
- **Strict schema**: unknown top-level keys are a startup error, so a cross-harness standard cannot keep its own keys inside `opencode.json`. They need a sidecar file.
- **Hooks are in-process JS functions**, not shell commands with a JSON stdin/exit-code protocol. Blocking = throwing; there is no Stop-hook "continue" decision and no SessionStart context return. A shell-hook standard needs a small adapter plugin that calls `$` and maps the result.
- **Permissions default to allow-all**, use **last-match-wins** ordering (Claude Code: deny beats ask beats allow regardless of order), and `run` auto-rejects every `ask`. A neutral rule set must be emitted in order, broad rules first.
- **Instructions are one-of, not additive**: `AGENTS.md` shadows `CLAUDE.md` (both global and project); no `@import`; nested `AGENTS.md` files are attached lazily when files under them are read.
- **Claude Code compatibility is on by default**: `~/.claude/CLAUDE.md` (when no global `AGENTS.md`), project `CLAUDE.md`, and `.claude/skills` are read. One skill tree can serve both harnesses, but there is cross-harness leakage unless disabled. No `.claude/commands`, `.claude/agents`, `.mcp.json` or `settings.json` support.
- **Client/server by design**: the TUI is a client of an HTTP server with an OpenAPI spec, SSE events and full session CRUD. Conformance tests can drive `opencode serve` or the SDK instead of a pty.
- **Sessions in SQLite** keyed by a project id derived from the git remote URL, not per-cwd JSONL transcripts; export via `opencode export` or `opencode db`.
- **Credentials in three places**: `auth.json`, `mcp-auth.json`, and DB tables (`account`, `credential`), plus `OPENCODE_AUTH_CONTENT` for env injection.
- **No status line**; TUI plugin slots (undocumented) are the extension point. TUI settings live in a separate `tui.json`.
- **Layered org control at both ends**: remote `.well-known/opencode` config is the *lowest* layer (tied to a provider login), managed files and MDM are the *highest*. This resembles Claude Code managed settings, but adds the remote base layer.
- **Docs drift**: docs and schema track `dev`. Stale items found: storage layout (JSON vs SQLite), npm plugin cache path (`node_modules` vs `packages`), `serve --port` default (4096 vs 0), `scout` agent (not in 1.18.18).

## What running OpenCode writes

- Even `opencode --version` and `--help` create the data directories at module load (§1),
  including an empty `repos/`, and open `opencode.db`. `debug` subcommands also write
  `log/opencode.log` and lock files under the state directory.
- So a survey or a test that runs the binary points every XDG variable (`XDG_CONFIG_HOME`,
  `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME`) at a scratch directory first, and checks
  that each override reached the process.
