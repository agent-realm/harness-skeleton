# Working on the session adapters

Conventions for any coding agent or human changing `packages/harness-session-adapters/`. The repo's
[`AGENTS.md`](../../AGENTS.md) applies on top of these.

harness-skeleton wraps this package in `hs` through the §7.3 shim, and does not keep a reader of
its own.

## Rules

1. **The contracts come first.** Records follow `sessions-model` v1, and the four operations
   follow `sessions` v1. If a harness cannot be expressed in them, propose the contract change
   there first. Never invent a field here without saying so in the code.
2. **One implementation.** `host` and `harness_path` are implemented here, for every consumer.
   No second copy anywhere.
3. **Imports.** Only `node:` builtins and this package's own files. Nothing from `hs`, memhouse or
   anything outside the package, and no dependencies. `test/workspace.test.js` at the repo root
   enforces it.
4. **Read-only toward the harness.** `read` opens files and databases read-only and never
   creates anything beside them: no `-wal`, no `-shm`, no lock. `derive` does no I/O at all.
5. **Redaction is the adapter's.** Values on declared paths are replaced in `read`, before a unit
   leaves the adapter, using the marker `<redacted len=N>`. Credential files are never opened.
6. **Determinism.** The same units give the same records, whatever the order of the sources and
   however the units are split across derive calls. The growth check in the conformance suite
   proves it for every fixture.
7. **Every fact carries a source.** A facet or a format rule cites a fixture, the harness's
   documentation (with the date it was read), or the harness version it was observed on.

## Fixtures are public

This repository is public. Fixtures hold synthetic content only:
- a generated toy repo, generated prompts and replies;
- the one home directory `/home/user`;
- documentation IP addresses and `example.com` mail.

Nothing is copied byte for byte from a real machine, and that includes a test machine's
captures: they carry the machine user's home, its addresses, host names, model gateway names,
session ids and local time zone, sometimes inside compressed or hash-addressed blobs. A fixture is one of:
- generated by a script under `fixtures/<harness>/`;
- a capture of a synthetic session on a test machine (a toy repo, invented prompts) with its
  environment strings, ids and time zone replaced **outside this repository** before it is
  copied in. The replacement list names
  the real values, so it never enters the repo. Text formats only: a binary, compressed or
  hash-addressed capture is rebuilt through the harness's own format instead.

**No model output from a capture.** Everything the model wrote in a captured session (replies,
reasoning text and summaries, encrypted reasoning, compaction summaries, generated titles and
previews, the request and response streams a harness logs) is replaced by synthetic ASCII text of
the same byte length, so offsets and positional ids stay put. Model ids are `gateway/toy-model`
(a letter suffix, `-a` to `-d`, tells several apart). No gateway address, port or server build
string stays. User prompts, tool names and arguments, and tool output keep the capture's shape.

`test/public-fixtures.test.js` scans every fixture, decoded base64 and compressed blobs
included. Where it can, it states what a fixture may hold rather than what it may not:
- a model field or a `gateway/` id names a toy model, a listed public vendor model or a listed
  placeholder;
- a time carries no offset other than UTC;
- a URL names no port.

It also refuses home paths other than `/home/user`, addresses outside the documentation ranges,
mail outside example domains, `.local` hosts and credential-shaped tokens. It never names a real
value, because naming one would publish it.

## Adding a harness

1. Write `src/harnesses/<harness-id>/{index.js, describe.js}`. The harness id is one of
   sessions-model §1 rule 3's registry; a new one is registered there first (a v1.x). Use `readStream` / `readSnapshot` from `src/sources.js` for file
   sources, and `seal` from `src/records.js` for every record.
2. Register it in `src/index.js`.
3. Write `fixtures/<harness-id>/generate.js` and its cases. Run `node conformance/golden.js
   <harness-id>`, and review every golden by hand before you commit it.
4. Write `test/<harness-id>.test.js`, modelled on `test/claude-code.test.js`. It covers the
   golden, the growth check, stable keys, the name lint, the reset control, `list`, the errors,
   and the explicit facets.
5. `npm test` from the repo root. CI runs the same.

The full walk-through, with every list a harness is registered in, is
[`docs/add-a-harness.md`](docs/add-a-harness.md).

## Install and deploy

The package is to be published to npm as `@agent-realm/harness-session-adapters`, for Node.js
22.15 or later. It has no dependencies of its own. Until it is on npm, use it from a checkout of
this repository, or pack it there (`npm pack` in this folder) and install the tarball. The
examples, the fixtures and the conformance suite will not be in the published package; use a
checkout for them.

```sh
git clone https://github.com/agent-realm/harness-skeleton
cd harness-skeleton
npm ci --ignore-scripts                   # hs's one dependency; this package needs none
npm test                                  # hs and every package, this one included
cd packages/harness-session-adapters
node examples/01-describe/describe.js     # the first example
```

- **In this repository**, `hs` imports it through the npm workspace.
- **In another project**, depend on it from npm once it is published (`npm install
  @agent-realm/harness-session-adapters`; until then, install the packed tarball), then import it
  by name, with `import` or, from CommonJS, `require`:

  ```json
  { "dependencies": { "@agent-realm/harness-session-adapters": "^1.0.0" } }
  ```

  To work against an unreleased change, depend on a checkout instead, by a `file:` path to
  `packages/harness-session-adapters`.

  It ships `src/`, `LICENSE`, `NOTICE`, `README.md` and `package.json` (`files`). `examples/`,
  `fixtures/`, `conformance/` and the tests stay in the checkout.
- **Against a real harness store** it only reads: `read` opens files and databases read-only and
  leaves nothing beside them. [Read a store](docs/read-a-store.md) walks through a consumer's
  passes.
- **Upgrading** a consumer to a newer checkout: compare each harness's `adapter_ver` and
  `state_ver` with the ones it stored, and re-derive or refold as
  [Versions](docs/adapter-interface.md#versions) says. A key change carries a migration note in
  [`CHANGELOG.md`](CHANGELOG.md).

## Git and review

Branch and worktree conventions are the repo's. Each PR is one or a few harnesses. Every PR is
reviewed before it merges; answer each finding on its own thread, naming the commit that
resolves it.
